# Layers, distilled

Generated by `distill.mjs` from `glossary.md`, `the-world.md` and `general-rules.md`; not
edited by hand. No Why, Relies on or Provenance: what binds is here.

- The glossary below applies to this file only. A repository may define some terms otherwise;
  reading the rules and properties below with its meanings warps them.
- Forces: what the world does to a system. Properties: what holds anyway. *Against* names the
  forces a property holds against; *Except*, what it does not cover.
- A rule is its Scope and Statement read as one. Where the Scope does not hold, the rule says
  nothing. Where two Scopes hold, the narrower governs.
- MUST, MUST NOT: no deviation. SHOULD, SHOULD NOT: the default; deviating takes an ADR naming
  the rule id. MAY: a permission where another rule would forbid.
- Examples name files by their absolute path in the repository; `—` means unfinished.

## Glossary

### Business domain

**Business domain.** A company's main area of activity: selling tea online. The domain models it.

**Business rule.** What the business domain allows, requires or forbids: an order ships only once
paid.

### System

A system is one bounded context. It is code with its own domain and its own glossary. A code
repository may hold several. Another bounded context is another system, even when it is
imported in-process.

**Outside.** Other systems and third parties, the operating system among them, whether they
drive the system or it drives them: a store, a mail provider, the clock, the file system.

**Tooling.** Code that runs in no process of the deployed application: a developer CLI, a seed
script, a test that asserts about the source tree.

**Probe.** Code a process runs to report on itself rather than on a system: whether it is alive or
ready, its metrics. `/health`, `/metrics`.

### The layers

**Use case.** One goal a caller can reach through the system, and how the system responds.

- **Domain.** The model: business rules, schemas, specifications. It is pure and knows no runtime.
- **Service.** The application layer. It carries out the system's use cases. It holds no business
  rule of its own; the business rules are the domain's. What it holds is the sequence within one
  use case: what to load, which business rule to ask, what to save. Each use case either acts or
  answers.
- **Driven adapters.** Implementations of driven ports.
- **Driving adapters.** Callers adapted to driving ports.

In DDD vocabulary, domain is the model, service is the application layer, driving adapters are the
interface layer, driven adapters the infrastructure layer.

**Port.** An interface, never the code behind it.

- A *driven port* is a way out of the system. Send a mail, save to the database, read from disk.
- A *driving port* is the way in. It names one use case the system offers and what a caller must
  bring, in the system's terms, not its store's. It does not know how it is reached.
- Who starts the call decides which. Seen from the caller, this system's driving port lies
  behind one of the caller's driven ports.

**Adapter.** Code on the far side of a port.

- A *driven adapter* implements a driven port. A port may have several: a database today, another
  store or a fake tomorrow. Swapping one changes nothing on the system's side of the port.
- A *driving adapter* adapts one caller to a driving port. There are as many driving adapters as
  there are ways into the process, like a server function, a CLI command, a webhook.

### Between systems

**Message.** What one system tells another, or itself, so that it may act. It has an id, the same on
every delivery of it. An *event* says something happened; no receiver can refuse it. A *command*
says do this, to the one system that offers it, which may refuse. *Published*: meant for other
systems. *Private*: meant only for the system that wrote it.

**Outbox.** Where a system's outgoing messages wait until they are delivered. The *outbox port* is
the driven port a service writes messages through. The *outbox reader* is what the relay reads the
outbox through, and marks it by; the system provides it, and for an external system's outbox,
assembly does.

**Handler.** A driving adapter that acts on messages delivered to its system.

**Bus.** What delivers a message to the handlers subscribed to it. Assembly hands it the handlers.

**Relay.** The mechanism that reads outboxes and hands each message to the bus. Assembly hands it
the outbox readers.

**Idempotent.** An operation is idempotent when repeating it leads to the same result as performing
it once.

**Tentative operation.** A request to another system for a commitment that leaves open the
possibility of cancellation. It changes nothing it asks for: its confirmation does.

**Open host service.** The driving ports a system offers to other systems.

**Published language.** What another system needs to talk to this one, or to translate from it:
the schemas, types and errors its open host service's driving ports take, return and raise, the
events it publishes, and the commands it takes from other systems.

**Reconciliation.** A use case that compares, after the fact, what this system recorded with what
another system holds, and repairs this system's record, or starts the step that repairs the
other's.

**Saga.** A sequence of steps across systems where, when a later step fails, new steps undo the
earlier ones.

**Choreography.** Each system reacts to the others' events and decides for itself what to do next.
No one holds the whole sequence.

**Orchestration.** One system's *process manager* holds the sequence across systems: an aggregate
whose state is where the sequence stands. Each step is a use case of that system that sends
commands to the others.

### Other systems

**Upstream system.** Of two systems that talk, the one the other depends on: it offers the open
host service the other calls, the commands the other sends, the events the other handles, and the
published language both are written in. It changes on its own terms.

**Downstream system.** The one that depends on the upstream: it calls the upstream's open host
service, sends its commands, handles its events, and adapts to its changes.

**Conformist.** A downstream system that takes the upstream as it is: its ports become the
downstream's driven ports and its published language is used untranslated, in any layer including
the domain.

**Anti-corruption layer.** A downstream system that translates the upstream's published language
into its own in every adapter that touches the upstream: the driven adapters that call into it and
the driving adapters it calls into. The upstream's terms stop at those adapters.

**Shared kernel.** A model several systems of this codebase share as code and agree on together,
each importing it into its domain: `Money`, `Sku`. A change to it is a change to each.

**Hook.** A driving adapter an upstream system calls.

**External system.** A bounded context whose code this codebase does not write, though it may
configure it: bought or adopted, run by its vendor or by us, in its own process or in ours. Its
configuration may hold business rules this codebase writes, in the external system's terms; its
architecture stays its own. It is driven through its API and driving through its hooks.

### Domain

**Aggregate.** A cluster of records changed as one unit and addressed by one id; a repository loads
and saves it whole.

**Owner.** The system whose business rules decide what a record holds, wherever it is kept; of a
record no business rule decides, the system that keeps it. A store may keep records of several
owners. A replica's records are its keeper's; what they copy stays the owner's to decide.

**Specification.** A domain function that answers yes or no about one candidate: is it valid, may
this happen, does it qualify.

**Repository.** A specialized driven port over exactly one aggregate: loads it, saves it, finds it.

**Snapshot.** A value an aggregate copies from another aggregate or from a message when a use
case needs it, and keeps as its own fact from then on: the price the order was placed at.

**Replica.** A copy of another system's data, kept under the owner's ids and shaped as this system
writes it: translated, compacted or projected. It is refreshed from what the owner publishes or
returns to it, and lags the owner.

### Driven adapters

**Record.** What a store holds and a write changes: a row in a relational store, its equivalent in
another.

**Store.** What lies behind one or more driven ports whose writes can be committed in one
transaction. Two clients are one store when their writes commit together, two stores until they
do.

### Driving adapters

**Scheduled task.** A driving adapter the clock calls.

**Ambient value.** A value a function reads without receiving it as an argument. Two scopes: per
process, set once for the process's life, like what assembly produced, a ready-made logger or an
environment variable; per request, what the current request carries, like a request id, a trace
context or a locale.

**Courier.** How a driving adapter reaches what assembly produced when assembly cannot hand it over
as an argument. Example implementations are per-process ambient values or the stack's context
objects.

### Assembly

**Factory.** A function that takes what an implementation needs and returns it. A service is a
factory for a driving port; an adapter's constructor is a factory for a driven port.

**System builder.** The part of assembly a system provides, so that a process's assembly builds
what it needs of the system without knowing its internals or their defaults: it takes
configuration and returns implementations. A system may have several, and one may return one
thing or many.

**Assembly.** The one place in a process where every port gets its implementation, and the only
place where port and implementation meet. It calls the system builders and produces what the
process's driving adapters call into.

**Common library.** Plumbing every system may import: store clients, a logger, a tracer, the relay,
the bus, the courier.

### Tests

**Fake.** A working implementation of a port that reaches nothing outside the process: a
repository over an in-memory map.

**Integration test.** A test that uses a real external dependency running where the test runs: a
database or a broker in a container.

**End-to-end test.** A test that uses a real external dependency running elsewhere: an external
system's own service, such as Stripe in test mode, or a mail provider's sandbox.

**Default suite.** The tests run by default: every test that is neither an integration test nor an
end-to-end test.

## The world

### Scope

Code split into systems, each one bounded context (glossary: System), run as one or more
processes. Each system keeps its records in a store, and what a store commits survives any stop
of a process. Systems reach each other through calls and messages; some are external systems.

Out of scope: throughput and load, security, user interfaces.

### Forces

- **F1. What lies behind the ports changes.** A store, a mail provider, a framework is replaced;
  a new caller arrives: a CLI command, a webhook, a test.
- **F2. The business changes, and so does what is known of it.** Business rules change, the
  model grows, the cut between systems moves.
- **F3. Edits are partial.** People and agents change code having read only part of it.
- **F4. Processes stop and are replaced.** A process can stop between any two of its
  instructions: a crash, a deploy, a timeout. A deploy replaces processes one at a time, and
  records and messages outlive the code that wrote them.
- **F5. Delivery repeats and reorders.** A message can arrive more than once, a redelivery while
  the first attempt still runs, and after one sent later.
- **F6. Callers overlap.** Two use cases can run against the same records at once.
- **F7. Other systems fail.** Another system can be down, slow, or fail after it said yes.
- **F8. Other systems change.** Another system's model and published language change on its
  schedule, not this one's.
- **F9. External systems offer what they offer.** An external system holds none of these
  properties, and its contract follows its own model: "take it or leave it" (Khononov, pdf 79).

### Properties

**P1.** The domain models the business domain, not what serves it
*Except:* another system's model this system chose to take (P12).
*Against:* F1.

**P2.** A business rule lives in one place: the domain
*Against:* F2, F3.

**P3.** Business rules that change together sit together; rules that change for different reasons share nothing either would have to change
*Against:* F2.

**P4.** A use case responds the same whoever calls it and whatever serves it
*Against:* F1.

**P5.** A system reaches the outside, and is reached from it, only through its ports; each port speaks the system's terms
*Against:* F1, F3, F8.

**P6.** Every use case can run with nothing outside the process
*Against:* F1.

**P7.** A use case's writes to its own system's records land together or not at all
*Against:* F4.

**P8.** An uncommitted write is not yet a fact: nothing final follows from it before it commits, and nothing that follows from it is lost after
*Against:* F4.

**P9.** A repeated delivery changes nothing in this system
*Against:* F5, F9.

**P10.** A use case commits only on reads that still hold, or on stale ones a business rule accepts; use cases fail each other only where a business rule ties them
*Against:* F6.

**P11.** No other system changes the records a system owns
*Against:* F8.

**P12.** Another system's model enters this one only by choice
*Against:* F8, F9.

**P13.** A system changes its model without its downstream systems changing
*Against:* F8, seen from upstream.

**P14.** A record or a message means the same to all code that reads it, whenever it was written
*Against:* F4, F8.

**P15.** A system works while others are down or slow, as far as its own data reaches
*Against:* F7.

**P16.** No transaction spans two systems
*Against:* F8.

**P17.** Work spanning systems ends, and only in a state a business rule allows
*Against:* F4, F7.

**P18.** The order messages arrive in does not change the outcome
*Against:* F5.

## General rules

### Assumptions

This document assumes a store that can be read and written, that can apply several writes atomically
where it says *transaction*, and that can make a write fail where the record has changed since it
was read, or where a record with the same key exists. It assumes no isolation between transactions
beyond reading committed writes: a transaction may read what another commits while it runs.

Every system gets the same architecture: domain, service, repositories and adapters, a simple one
too. That is this document's choice. The sources pick the architecture per subdomain and let
simple logic read and write the store directly; here no system is judged simple enough, and none
is rewritten when it grows business rules.

Not everything gets a layer. Assembly, a system's export paths and the common library sit outside
the layers. So do probes.

Tooling sits outside the layers and the rules. It builds systems through their builders or
replaces their internals: an in-memory outbox, a CLI as relay and bus. What it reaches past an
export path is no offer (SYS-1), and a system changes it without notice.

An external system sits outside the rules: its exports, its layers and its transactions are its own,
even where this codebase writes its configuration. What a system of this codebase does with it is
inside them: the adapters that call it, the hooks it calls, and the parts of its configuration that
touch the system: what may change the system's records it keeps (SYS-12), how it tells the system of
a change (TX-29).

Not covered: where UI code goes, which is `components.md`; library, framework and file-naming
conventions, which are the stack document's; whether a module that straddles two layers should be
split now; whether a downstream conforms to an upstream or builds an anti-corruption layer, and
whether work spanning systems is choreographed or orchestrated, which a repository's ADRs decide;
how a driving adapter is tested, and when the integration suite runs, which are the repository's;
how the bus finds a message's handlers, by its type or by each handler filtering, which is the
stack document's.
